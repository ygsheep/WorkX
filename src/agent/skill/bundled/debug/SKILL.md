# Debug — 系统化调试

有纪律的排障流程。**先建立可判定信号，再谈定位与修复。**

## Phase 1：建立反馈环（核心）

**先找到一个"能稳定复现问题、且能区分对错"的最短命令/测试。** 这是整个调试的关键：

- 优先做一个当场能复现该 bug 的失败测试、脚本或命令

- 信号的判定标准：能对**这个具体 bug** 从红变绿，而不是"能跑通就行"

- 尽量快、确定、可无人值守地反复运行

没有这个信号之前，不要急着猜原因、改代码——那是本技能要防止的最大错误。

## Phase 2：复现并最小化

- 运行反馈环，确认它复现的是**用户描述的症状**，不是恰好邻近的另一个错误

- 逐步删减输入/环境/步骤，每删一次都重跑，只保留"少了它就不复现"的元素

## Phase 3：多假设

- 列出 **3\~5 个**可证伪的假设，每个都给出预测："若 X 是原因，则改动 Y 后 bug 会消失/更糟"

- 逐个验证，一次只变更一个变量

## Phase 4：插桩

- 优先用调试器/REPL 单点检查，其次才是针对性日志

- 调试日志加唯一前缀（如 `[DBG-x1]`），修完统一 grep 清理

## Phase 5：修复 + 回归

- 在**正确的层次**写回归测试（能真正覆盖 bug 触发链路的那层）

- 先看着它失败 → 修复 → 看着它通过 → 再用 Phase 1 的原场景复验

## Phase 6：收尾

- [ ] 原始场景不再复现（重跑 Phase 1 反馈环）

- [ ] 回归测试通过（或记录"无正确缝合层"的结论）

- [ ] 清理所有调试插桩

- [ ] 在提交/PR 里写明真正的原因，帮助下一个调试者
